## 1. 现状基线核查

### 1.1 数据层
- `data/games.js`：6 条记录 + `withAssets()`（拼 8 个素材 URL：icon/portrait/header/hero/logo + 3 张截图）+ `GAME_MAP` + `pickFeatured()`（评分最高，平手取声明序）。
- 元数据（rating / owners / sizeMB / tags / developer / releaseDate / playtimeHrs / lastPlayed）**只随数据文件分发，不进 localStorage**（C1 决策）。这是本次扩容最大的兼容红利：**新增字段零迁移成本**。
- `lib-rules.js` / `download-engine.js` / `library.js` 全部按 `gameId` 工作，不感知目录规模。

### 1.2 商店页当前实现（关键约束）
- `.rail` 在 `/store` 隐藏（`shell.js:128-131`），`#view` 占满整宽：1920 内容宽 1872（7 列），1280 内容宽 1232（5 列），`grid-template-columns: repeat(auto-fill, minmax(230px,1fr))`，gap 16。
- 卡片结构：`card__cover`（140px，`card__rating` 左上、`card__size` 右上、`card__status` 左下）+ `card__body`（name / hook / tags）。按样式推算单卡高 ≈ 250px（cover 140 + body ≈110）。
- 卡片状态徽标由 `state/store.js` 订阅刷新，`statusRefs: Map<gameId, Element>` 在**建卡时**登记一次。
- 搜索过滤用 `grid.querySelectorAll('.card')` 的**下标**回查 `GAMES[i]` —— 与「按条件重排/重渲染」天然冲突（详见 §3.5）。

### 1.3 垂直空间账（决定 §3.4 的整改数值）
视口 1280×720：`titlebar 34 + topnav 52 + statusbar 42 = 128`，`#view` 高 592，内容上边距 18。
- 页头（h2 34 + sub 20 + 2 + margin 22）≈ 78
- 焦点位 300 + margin 22 = 322
- 卡片区起点 ≈ **418**，可见区仅 174px < 单卡 250px → **现状 1280×720 首屏第一行卡片就是被裁切的**（与 `fresh_store_1280x720.png` 一致）。
- 若再加一行 chips（36 + 12 = 48），可见区只剩 126px（只够封面）→ 不可接受。

## 2. 数据模型变更

### 2.1 新增字段（唯一权威表）

| 字段 | 类型 | 必填 | 说明 | 消费方 |
| --- | --- | --- | --- | --- |
| `category` | `string` 枚举 | **是** | 唯一主分类，取值必须 ∈ `CATEGORY_KEYS`（7 个） | 商店 chips 筛选、详情页事实行 |
| `isAdult` | `boolean` | **是（显式声明 false）** | 是否 18+ 内容；**不设默认值**，漏写即被契约测试拦下 | 年龄门、焦点位排除、卡片 18+ 标识、`aria-label` |

现有字段**全部保留**、语义不变：`id / name / emoji / gradient / hook / desc / tags / sizeMB / rating / owners / publisher / developer / releaseDate / playtimeHrs / lastPlayed / assets`。

`tags` 继续作为自由文本（展示 + 搜索命中），**不**承担分类职责：分类是单值枚举，标签是多值描述。二者不可互相替代，也不做映射同步。

### 2.2 明确不新增的字段（及理由）

| 候选字段 | 决定 | 理由 |
| --- | --- | --- |
| `studioId` | 不加 | 当前没有任何「按工作室浏览 / 工作室页」的消费方。`developer` 已满足展示与送礼弹窗。加 18 份冗余键 = 纯维护成本，且要与 `developer` 双写（漂移风险） |
| `featured` | 不加 | 焦点位规则保持「评分最高且非成人」。加布尔字段会让「谁上焦点」出现两个真源（数据 + 代码） |
| `batch` | 不加 | 批次是**交付环节**的元数据，不是领域数据。落进运行时会被页面/测试误用；批次进度由本文 §7 追踪 |
| `ageRating: '18+'` | 不加 | `isAdult` 单一真源，`18+` 文案由 `isAdult` 派生。两个字段必然漂移 |
| `categoryLabel` | 不加 | 文案属 `categories.js`，每款重复 18 份中文标签 = 改文案要改 18 处 |
| `sortRank` / `catalogOrder` | 不加 | 数组声明序即展示序，显式排名是第二真源 |
| `shortName` / `aliases` | 不加 | 无需求；搜索走 name/tags/publisher 已够 |

### 2.3 兼容策略（为什么这次扩容不需要状态迁移）

1. **游戏元数据不在 localStorage**（仅 `library/downloads/gifts` 里存 `gameId` 引用），因此新增字段对已安装用户的存量状态零影响，无需 `normalize()` 增补、无需 bump version。
2. **旧 6 个 `id` 冻结**：`stardust-miner / cloud-bakery / neon-drift / corridor-seven / orbit-market / echo-archive` 不得改名、不得删除。新增契约测试断言「这 6 个 id 必须仍存在且字段齐全」，把「改名」这种静默破坏挡在 CI。
3. **页面读取用保守写法**：`const cat = g.category || 'unspecified'`，`const gated = g.isAdult === true`。枚举合法性由测试保证；运行时即使数据脏也不崩，最多该款只在「全部」下可见（可发现性 fail-open，安全性由测试 fail-closed 保证）。
4. **规模数字禁止硬编码**：`store.js` 的「6 款虚构游戏」改为读 `GAMES.length`，`README` / `badges.js` 的「六款」一并处理（§6）。
5. **新增占位 id 规范**：内容定稿前用 `new-a1…new-a4 / new-b1…new-b4 / new-c1…new-c4`，合入前必须换成 kebab-case 真实 slug（契约测试校验 `^[a-z0-9]+(-[a-z0-9]+)*$`）。**占位 id 不得进版本库主干**。

### 2.4 分类枚举（`data/categories.js` 契约）

```
CATEGORIES = [
  { key: 'rpg',        label: '角色扮演', order: 1 },
  { key: 'shooter',    label: '射击',     order: 2 },
  { key: 'action',     label: '动作',     order: 3 },
  { key: 'strategy',   label: '策略',     order: 4 },
  { key: 'simulation', label: '模拟',     order: 5 },
  { key: 'casual',     label: '休闲',     order: 6 },
  { key: 'tools',      label: '工具',     order: 7 },
]
CATEGORY_KEYS  = CATEGORIES.map(c => c.key)      // 校验/筛选的唯一真源
CATEGORY_MAP   = Object.fromEntries(...)          // key → {label, order}
```

- 旧 6 款的分类归属是**产品决策**，由内容设计侧给出，本文不替其拍板。工程只锁「取值必须合法」「每个分类最终至少 1 款」。
- `tools`（工具）在商店里与游戏同列展示，但**不参与**「游戏库/已获取」的任何文案重定义——库页仍叫「游戏」，只是其中可能包含工具类条目。这是刻意接受的语义松弛，避免为一个演示项重构库页。

### 2.5 单文件 vs 按分类拆文件（取舍）

| 方案 | 做法 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| **A 单文件（推荐）** | `data/games.js` 内 18 条，按 `category.order` 分组排列 | 0 处 import 改动；`withAssets`/`GAME_MAP`/`pickFeatured` 位置不变；测试无需改导入路径；18 条 ≈ 300 行仍可读 | 3 批并行改同一文件 → 冲突面集中；review diff 较长 | **采用** |
| B 按分类拆 | `data/games/{rpg,shooter,…}.js` + `data/games/index.js` 聚合后 `withAssets` | 每类一个文件，责任清晰，冲突面小 | 改 8 处 import 路径；聚合顺序 = 展示顺序，隐含耦合；7 个文件装 18 条（平均 2.5 条/文件）过度设计；`assetUrl` 相对路径基准位置变化，素材 URL 易错 | 暂不采用 |
| C 按批次拆 | `data/games/batch-a…c.js` | 与交付节奏一致 | 批次是交付概念，不是领域概念；批次文件命名会永久留在代码里；后续增减内容要跨文件搬移 | 拒绝 |

**决策 A + 明确的拆分触发条件**（满足任一即写 ADR 后再拆）：
- `data/games.js` 超过 400 行；或
- 同时有 ≥2 名作者在并行新增目录数据（当前是内容侧一人出稿、工程一人合入，不满足）。

### 2.6 数据契约测试（新增 `tests/catalog.test.js`）

1. `id` 唯一、符合 kebab-case、旧 6 个 id 全部存在；
2. 每款 `category ∈ CATEGORY_KEYS`（必填，不接受 `undefined`）；
3. 每款 `typeof isAdult === 'boolean'`，且 `isAdult === true` 的款数 ≤ 1（最终态）；
4. 每款 `assets` 8 个文件落位、`header ≠ portrait`（沿用现有断言）；
5. 每款 `rating ∈ (0,5]`、`sizeMB > 0`、`owners > 0`、`tags.length ≥ 1`；
6. 最终态（C 批合入时启用）：每个 `category` 至少 1 款（避免出现点进去永远空的 chip）；
7. `pickFeatured(GAMES)` 返回非成人款（见 §6.3 T2）。

## 3. 分类与筛选：信息架构

### 3.1 三个候选方案

**方案 A（推荐）：焦点位 + 分类 chips + 全部网格**

```
[商店]  [全部][角色扮演][射击][动作][策略][模拟][休闲][工具]        [搜索 ............]
18 款虚构游戏 · 全部本地数据
┌──────────────── 焦点推荐（非成人，评分最高） ────────────────┐
└──────────────────────────────────────────────────────────────┘
┌卡┐┌卡┐┌卡┐┌卡┐┌卡┐┌卡┐┌卡┐     ← 受 chips + 搜索共同过滤
└──┘└──┘└──┘└──┘└──┘└──┘└──┘
```
- 优点：唯一同时满足「按分类缩小范围」与「一屏可扫全量」的方案；DOM 结构改动最小（页头加一行、网格加 `hidden` 切换）；可访问性天然好（`<button aria-pressed>`）。
- 缺点：18 款仍要滚动（1280 下 4 行）。

**方案 B：分组网格（分类标题 + 每类一段网格，chips 变锚点）**
- 优点：「逛」的体验最好，分类结构一眼可见，无隐藏内容，无需筛选状态；可访问性最好（页内锚点）。
- 缺点：没有真正的「筛选」，与需求「分类与筛选」只答了一半；18 款全展开约 1700–2200px 长页；chips 需 `scroll-margin-top` 与粘性头部配合；批次未满时会出现「2 款一段」的碎片感。

**方案 C：Steam 式分类横向行（每类一行，横向滚动）**
- 优点：视觉最丰富，最像成熟商店。
- 缺点：横向滚动在桌面端的可发现性差，键盘/触控板操作成本高；每类行需要独立滚动容器与边缘渐隐；视觉基线几乎全部重做；实现与测试成本约为 A 的 2.5 倍。

| 维度 | A | B | C |
| --- | --- | --- | --- |
| 满足「筛选」（缩小范围） | ✅ | ❌（仅定位） | 部分 |
| 首屏信息密度（1280×720） | 中 | 高 | 中 |
| 实现成本 | 低 | 中 | 高 |
| 视觉基线重做量 | 8 张 | 8 张 + 长页 2 张 | 26 张全量 |
| 可访问性风险 | 低 | 低 | 中（横向滚动容器） |

**推荐 A。** 若设计侧明确「以逛为主、弱化筛选」，可退到 B（此时 chips 的 `aria-pressed` + 过滤逻辑要整段删掉，不要保留双模式）。

### 3.2 推荐方案的 DOM / 结构约定（签名级，不含实现）

- 页头一行三块：`标题+副标题`（左，flex 1）/ `分类 chips`（中，可换行）/ `搜索框`（右，~200px）。
- chips：`<nav aria-label="分类筛选">` 包裹 8 个 `<button class="chip" aria-pressed="true|false" data-cat="all|rpg|…">`。单选，`全部` 默认 `aria-pressed=true`。
- 网格：**18 张卡片一次性建好常驻 DOM**，过滤只切 `hidden` 属性，不重建、不排序。
- 空结果：网格内插入一个常驻的 `<div class="grid__empty" hidden>`，文案「没有匹配的游戏 · [清除筛选]」；按钮一次清空 chips + 搜索。

### 3.3 筛选状态放哪：`state/ui.js`（决定 D5）

| 方案 | 评价 |
| --- | --- |
| **`state/ui.js`（推荐）** | 与 `sidebarFilter/sidebarSort` 完全同构（已有先例、已有 subscribe 模式）；会话内跨路由保留（商店→详情→返回，筛选还在，符合直觉）；重启归零，不污染 localStorage，不进导出 JSON |
| `settings` 持久化 | 用户偏好类（如「默认只看已安装」）才值得持久化。分类筛选是一次性浏览动作，持久化会导致「上次只看了工具，这次打开商店只有 1 款」的困惑，且给 `normalize()`/导出/重置增加 4 处触点 |
| 页面局部变量 | store→detail→back 会重建页面，筛选丢失；且无法被其他模块（如未来的「按分类查看」入口）复用 |

新增接口（与现有风格一致）：`getStoreCategory()`、`setStoreCategory(key)`（非法 key 忽略）、`subscribeStoreCategory(fn)`。默认 `'all'`。

### 3.4 与现有 UI 的共存规则

1. **搜索**：新增页面内 `#store-search`（**不要复用 `#search-input`**，那是左栏的、且在商店页是 `hidden` 的）。输入即过滤（保持现有零防抖手感，18 条无需防抖）。搜索命中字段：`name / tags / publisher`（与现状一致）。
2. **筛选 ∩ 搜索 = AND**：卡片可见 ⟺ 匹配搜索 且（分类=全部 或 卡片分类=当前分类）。
3. **`下载中 N%` / `已在库中` 卡片态**：卡片常驻 DOM，`statusRefs` 只在建卡时登记一次 → 订阅刷新逻辑**完全不改**；过滤只切 `hidden`，不销毁节点，因此下载进度不会因筛选/搜索而停止更新。这是选择「常驻 + hidden」而非「重渲染」的核心原因。
4. **订阅与筛选的顺序**：`updateStatus()` 只写 `textContent/className`，不碰 `hidden` → 与过滤互不干扰。
5. **左栏搜索**：仍在 `/library` 生效，互不影响（两个 input 不同 id、不同事件模型：shell 用 `addEventListener`，store 用 `oninput`）。
6. **切页清理**：`onLeave` 中解绑 `#store-search` 监听 + 取消 store 订阅（沿用现有模式），但**不清空** `ui.js` 里的分类（跨页保留）。

### 3.5 必须修掉的下标耦合

现状 `grid.querySelectorAll('.card')` 的下标 → `GAMES[i]`。一旦过滤后重排/重渲染就错位。整改为：卡片写 `data-game-id`，过滤与状态回查一律走 `GAME_MAP[card.dataset.gameId]`。这条即使不扩容也该修，扩容后是硬前提。

### 3.6 1280 宽下的排版整改（带数值）

| 措施 | 数值 | 效果 |
| --- | --- | --- |
| chips 并入页头行（不新增行高） | 0px | 省 48px；1280 宽度下 8 个 chip + 标题 + 搜索 ≈1020px < 1232px，单行放得下 |
| 焦点位在窄窗口降高 | `@media (max-width:1400px) { .storehero { height:220px } }` | 省 80px；同时 `storehero__name` 30→24px、`hook` 隐藏或 1 行 |
| 卡片区起点 | 18+78+220+22 = **338** | 可见区 254px ≈ 完整一行（250px） |
| 单卡紧凑化（可选，C 批） | `@media (max-width:1280px)`：cover 140→120、hook 限 1 行（`-webkit-line-clamp:1`） | 单卡 250→205，4 行由 1048 → 868px |

**验收口径（写入 A 批故事）**：1280×720 下，首屏必须完整显示一行卡片（5 款）且 chips 不被裁切；1920×1080 下首屏可见 ≥2 行（14 款）。

## 4. 18+ 年龄门

### 4.1 拦截发生在哪一层（决定 D6）

| 候选 | 评价 |
| --- | --- |
| 商店卡片点击时拦截 | ❌ 只挡点击路径。直接 `#/detail/adult`（刷新、外部链接、历史前进）绕过；`location.hash` 手改也绕过 |
| 路由守卫（router 增加 `beforeEach`） | 结构上最正确，但 router 是零依赖 40 行模块，加守卫必须让它认识「哪条路由需要什么条件」→ router 反向依赖 `GAME_MAP` 与状态，耦合变重；当前只有 1 条路由需要门禁，收益不抵成本 |
| **`renderDetail` 渲染前拦截（推荐）** | 在 `view.innerHTML` 写入任何内容之前判断，**成人内容零闪现**；对 hash 直接访问、历史前进、刷新一律生效；不碰 router 匹配逻辑 |
| 详情页 render 后遮罩 | ❌ 内容已进 DOM，截图/读屏/快速点击都可能先暴露 |

**实现形态**：`renderDetail(view, params)` 顶部判定 → 未确认则只渲染门禁屏（无任何该游戏的图/描述，仅标题文字），并打开门禁弹窗；确认后重新进入渲染。

确认后的「重新渲染」不要用递归或伪造 hash，给 `router.js` 增加：

```
export function rerender() { render(); }   // 复用现有 render()，先 onLeave 再重入
```

3 行、零新依赖、可测试（`rerender()` 后 `current.onLeave` 被调用一次）。这是本次唯一允许触碰 router 的改动。

### 4.2 状态存哪（决定 D7）

| 方案 | 评价 |
| --- | --- |
| **`settings.adultGateConfirmedAt: number \| null`（推荐）** | 与「本机 / 设备级偏好」语义一致；`settings` 已在 `normalize`/`updateSettings`/`resetAllData` 三处有成熟管道；扁平字段，无需嵌套对象规范 |
| `settings.adultGate: {confirmed, at}` | 归一化要多写一层对象校验，收益为零 |
| `profile.adultVerified` | `profile` 语义是「本地访客的人设与成就」，年龄确认是设备策略不是人设；且 `buildExportPayload()` 会整包导出 `profile`，反而更难排除 |
| 独立 localStorage key | 破坏「单一状态键 + 统一 normalize/重置/导出」的架构约定，重置会漏清 |

**生命周期**

| 事件 | 行为 |
| --- | --- |
| 首次访问成人详情且 `null` | 弹门禁，不写任何状态 |
| 选「我已满 18 岁」 | 写 `Date.now()`，记事件 `adult_gate_accept`，`rerender()` 进详情 |
| 选「未满 18 岁」/ Esc / 点遮罩 | **不写状态**，记事件 `adult_gate_decline`，`location.hash='#/store'` |
| 再次进入 | `confirmedAt` 非 null → 直接进详情，不再询问（会话内与重启后都生效） |
| 清除方式 | ① 设置页「清除本地数据」（已有）；② （C 批可选）设置页新增「重新验证年龄确认」行，把字段置 `null` |
| 跨设备 | localStorage 天然按设备隔离；**同时**在 `buildExportPayload()` 中显式剔除该字段，避免「导出的 JSON 带到别的机器被误认为已确认」 |
| 版本兼容 | **不 bump `version`**：这是「可选字段 + 安全默认值（null）」演进，`normalize` 里加 3 行即可。⚠ 若将来必须 bump，**先改** `store.js:144` 的 `legacy = input.version !== 2 && input.version !== 3` 与 5 处 `assert version === 3`，否则 v4 状态会被当成 v1 legacy（favorites 迁移会误跑） |

**为什么全局确认而不是按游戏确认**：按游戏需 `{ [gameId]: ts }` 无界增长的映射，且第二款成人内容上线时要重新问一遍——与「设备上一个成年人」的现实语义不符。全局一次确认 + 可清除，是这里的最小正确模型。

### 4.3 弹窗与可访问性（含「未满 18」分支）

- 新增 overlay `#age-dialog`（结构与现有 `#install-dialog` 同族）：`role="dialog" aria-modal="true" aria-labelledby="age-title" aria-describedby="age-desc"`。
- 文案骨架：标题「内容分级提示」；描述「《X》仅向年满 18 岁的访客展示。本客户端为离线虚构演示，不包含真实付费或下载。」
- **门禁屏不显示任何该游戏的封面/截图/描述**（避免未经确认即展示成人素材），只出现游戏名与分级标识。
- 按钮顺序与焦点：
  1. DOM 顺序「我已满 18 岁」→「未满 18 岁 · 返回商店」；
  2. **初始焦点落在对话框容器**（`tabindex="-1"`），不落在任何按钮上 —— 避免空格/回车误确认；
  3. Tab 循环限制在两个按钮内（焦点陷阱），`Esc` **等价于未满 18**（fail-closed）；
  4. 点遮罩 = 未满 18（与现有弹窗「点遮罩关闭」习惯一致，但语义是拒绝而非关闭）。
- 返回商店后焦点交还：`.page__head h2`（`tabindex="-1"`）+ Toast「该作品需年满 18 岁才能查看」，避免焦点落到 `body` 导致读屏丢失位置。
- 触发源可发现性：成人卡片 `aria-label="《X》，18+ 成人内容"`，卡片封面右下角 `18+` 徽标（左上评分、右上体积、左下下载态已被占用，右下是唯一空位）。
- 颜色/动效：`18+` 徽标用 `--warn` 色系但不作为唯一信息载体（同时有文本 `aria-label`）；门禁出现遵守 `reduced-motion`（无缩放动画）。

### 4.4 边界矩阵（必须逐条手测/自动化）

| 场景 | 期望 |
| --- | --- |
| 商店点成人卡 | 门禁弹窗，商店 DOM 不变 |
| 冷启动直接 `#/detail/adult` | 只渲门禁屏；页面源码/DOM 中无成人素材 URL |
| 确认后刷新 | 直接进详情，不再询问 |
| 确认后 `history.back()` 再前进 | 直接进详情 |
| 未满 18 后点浏览器后退 | 会回到该 hash → 再次弹门禁（可接受；不记忆拒绝） |
| 清除全部数据后进入 | 重新弹门禁（字段回 null） |
| 导出 JSON | `settings` 中**不含** `adultGateConfirmedAt` |
| 已安装的成人游戏从库页进入 | **不拦**（详见 §4.5） |
| 焦点位 | 成人款永不出现在焦点位（§6.3 T2） |

### 4.5 明确不做（非目标）

- 库页 / 库详情 / 下载页 / 启动流程**不加门禁**。理由：能进库就意味着「曾在商店详情确认过」（获取动作的唯一入口在详情页）。数据被手工篡改属于本地演示的接受范围，不为此增加 4 处拦截点与相应测试。
- 不做「未成年模式」「内容屏蔽开关」——超出本期范围，且会让分类筛选与门禁逻辑互相纠缠。

## 6. 现状缺陷与修正（与扩容强耦合，必须先修）

### 6.1 F1 商店搜索是死代码

- 事实：`index.html` 中唯一的 `#search-input` 位于 `.rail`（第 83–86 行）；`shell.js:128-131` 在非 `/library` 路由设 `railEl.hidden = true`；`.rail[hidden]{display:none}` 生效。
- 结论：商店页没有任何可见搜索框，`store.js:77-87` 从未被真实用户触发。
- 处置：A 批新增页面内 `#store-search`，删除对 `#search-input` 的绑定；保留左栏搜索原样。

### 6.2 T1 素材契约是硬门禁

- 事实：`store-flow.test.js` 遍历 `GAMES` 逐个 `existsSync` 8 个素材文件；`library-flow.test.js` 同时断言 6 款。
- 结论：**数据与素材必须同批合入**，且每批 4 款 = 32 个新文件。任何「先合数据占位、素材下批补」的做法都会让 CI 红。
- 处置：写进 A 批验收门槛（见 §7.1 的 A1 验收标准）。

### 6.3 T2 焦点位规则

- 现状 `pickFeatured` 取全量最高分。18 款里成人款很可能是高分作品（内容设计常用「话题作」定位）。
- 决定：`pickFeatured` 只在 `isAdult === false` 中取最高分；若全部为成人（不可能），回退到全量。
- 后果：详情页 hero 永不展示成人素材；`store-flow.test.js` 的「最高分」断言改为「非成人中最高分」。

### 6.4 徽章语义漂移

| 项 | 现状 | 处置 |
| --- | --- | --- |
| `shelf_all` 名称 | 「六款齐收」 | 「全数收藏」（4 字，与旧名等宽，减少 tile 换行风险；字形仍会变，基线照旧失效） |
| 条件文案 | 「集齐全部 6 款游戏」 | 「集齐全部收录游戏（18 款）」 |
| 已解锁用户 | 已持徽章 | **不回收**（本地无「回收」路径，且回收会让老用户困惑） |
| 计数口径 | `Object.keys(library).length` | 只计 `GAME_MAP` 内存在的 id |

## 9. 决策记录（ADR 摘要）

**ADR-01 分类为单值枚举，标签继续多值自由文本**
- 备选：多值 `categories[]`；分类即 `tags[0]`；单值枚举。
- 决定：单值枚举 + 独立标签。
- 后果：筛选语义清晰、chip 计数稳定；一款游戏若横跨两类，需产品判断主分类。不提供「多分类归属」。

**ADR-02 目录数据保持单文件**
- 备选：见 §2.5。
- 后果：3 批改同一文件，冲突面集中；用 §2.5 的量化阈值作为未来拆分依据。

**ADR-03 商店分类筛选是会话内 UI 态（`state/ui.js`）**
- 备选：`settings` 持久化；页面局部变量。
- 后果：不污染 localStorage / 导出 / 重置；重启归零；跨路由保留。

**ADR-04 年龄门在 `renderDetail` 渲染前拦截 + `router.rerender()`**
- 备选：路由守卫；点击拦截；渲染后遮罩。
- 后果：零内容闪现、覆盖直链与历史前进；router 只多 3 行；门禁判定逻辑集中在详情页，其他页面若将来需要门禁需重新评估（当前明确不做）。

**ADR-05 成人确认存 `settings.adultGateConfirmedAt`，不 bump version、不进导出**
- 备选：`profile` 字段；独立 localStorage key；按游戏映射。
- 后果：设备级一次确认；清除数据即失效；导出无法带走（符合「不跨设备」）；「未满 18」不落状态，允许重试。

**ADR-06 卡片常驻 DOM，过滤只切 `hidden`**
- 备选：按筛选重渲染网格；虚拟列表。
- 后果：`statusRefs` 与订阅逻辑零改动、下载进度不中断；18 个节点的开销可忽略；未来若到数百款再评估重渲染/虚拟化。

**ADR-07 焦点位排除成人内容**
- 备选：允许成人款上焦点但点开先门禁；加 `featured` 字段。
- 后果：hero 永不展示成人素材；规则仍由 `pickFeatured` 单点维护。

**ADR-08 徽章 `shelf_all` 改为全量语义、不回收已解锁**
- 备选：保留 6 款门槛（与 18 款现实矛盾）；改为「拥有任意 N 款」。
- 后果：新用户需集齐 18 款；老徽章保留；计数需过滤孤儿 id。

## 10. 实现控制清单（一页规则，给落地的人）

1. 数据：只加 `category`（必填枚举）、`isAdult`（必填布尔）。不加 `studioId`/`featured`/`batch`。
2. 数据与 8 个素材文件**同批合入**，否则 CI 红。
3. 旧 6 个 `gameId` 不得改；页面不得硬编码「6 款」「六款」。
4. 分类文案只来自 `categories.js`；页面里不写中文字面量。
5. 商店用 `#store-search`，**不要碰 `#search-input`**（那是左栏的，且在商店页不可见）。
6. 卡片一次性建全，过滤只切 `hidden`；禁止用 `querySelectorAll` 下标回查 `GAMES`。
7. 筛选状态只在 `state/ui.js`，不进 `settings`、不进导出。
8. 年龄门在 `view.innerHTML` **之前**判定；门禁屏不放任何该游戏的图/描述。
9. `settings.adultGateConfirmedAt` 用 `number|null`；「未满 18」不写任何状态；导出时剔除。
10. 不 bump `version`。若一定要 bump，先改 `legacy` 判定和 5 处版本断言。
11. 徽章计数只算 `GAME_MAP` 里存在的 id。
12. 每批必须跑：`npm test` 全绿 + `visual:compare --only <受影响>` 0 差异 + 双视口截图人工目检。
